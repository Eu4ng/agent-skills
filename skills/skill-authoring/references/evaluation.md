# 스킬 평가

두 가지를 본다. 스킬이 필요할 때 켜지는지(트리거)와, 켜졌을 때 결과가 스킬 없을 때보다 나은지(품질)다.
평가 결과물은 저장소 밖 임시 작업 폴더에 둔다.

## 저사양 로컬 모델 점검 (기본)

성능 좋은 모델은 흐릿한 설명과 지시도 알아서 메워 잘 동작한다. 그래서 그 모델로만 확인하면 스킬의 결함이
드러나지 않는다. **작은 로컬 모델에서도 동작하는 스킬이 잘 쓴 스킬이다.** 스킬을 만들거나 고치면 먼저 이
점검을 한다.

모델 서버 주소와 모델 이름은 `~/.agents/environment.md` 의 `## 로컬 LLM` 절에서 읽는다. 없으면 사용자에게
묻고 그 절에 적는다. 스크립트는 표준 라이브러리만 쓴다. Ollama 기본 API 와 OpenAI 호환 API 를 지원한다.

1. 스킬 폴더에 `evals/triggers.json` 을 둔다. 형식은 `[{"query": "...", "expect": "<스킬 이름>" 또는 null}]` 이다.
   켜져야 하는 질의와, 키워드는 겹치지만 다른 작업인 근접 오답 질의를 반씩 넣는다.
2. 트리거를 점검한다. 설치된 다른 스킬도 함께 목록에 올려야 실제처럼 경쟁한다.

   ```bash
   python3 scripts/local_eval.py trigger --skills <스킬 폴더들> --queries <triggers.json> --runs 5 \
     --base-url <서버> --model <모델>
   ```

3. 실행을 점검한다. `evals/evals.json` 사례에 `checks`(작업 폴더에서 실행할 확인 명령, exit 0 이면 통과)를
   적어 두고 돌린다. `run_command` 는 모델이 만든 명령을 그대로 실행한다. 그래서 `--allow-commands` 는 버려도 되는
   작업 폴더에서만 쓴다. 모델에게 보이는 홈은 `<작업 폴더>/<사례>/home` 이다. 스킬은 `<작업 폴더>/_skills/` 에 복사한
   사본으로 보여 준다. 실제 스킬 저장소의 경로를 모델이 알면 명령으로 그 안에 파일을 만들 수 있기 때문이다.

   ```bash
   python3 scripts/local_eval.py run --skills <스킬 폴더들> --evals <evals.json> --workdir <임시 폴더> \
     --allow-commands --output <대화 기록.json> --base-url <서버> --model <모델>
   ```

4. 요약 JSON 에서 다음을 본다. 대화 기록에서 모델이 헤맨 지점을 찾아 스킬 문장을 고친다.
   - `skills_read`: 스킬을 읽었는가
   - `commands`: 스킬이 정한 검증 명령을 실행했는가
   - `checks`: 결과가 통과했는가
   - `asked`: 물어야 할 것만 물었는가
5. 결과를 남긴다. 두 명령에 `--record` 를 붙이면 각 스킬의 `evals/results.json` 에 모델별 결과가 남는다. 남는 항목은
   통과 수, 실패한 질의·확인 명령, 날짜, API, 스킬을 켠 방식이다. 같은 모델의 이전 결과는 새 결과로 바뀐다.
   경로 같은 환경 정보는 남지 않으므로 커밋해도 된다.
   기록된 결과는 `python3 scripts/local_eval.py report --skills <스킬 폴더들>` 로 표로 본다. `현재 판` 이 `아니오` 인
   줄은 SKILL.md 가 바뀐 뒤라 다시 점검해야 하는 결과다.
6. **여러 모델로 되풀이한다.** 테스트는 스킬 안에 있으므로 `--model` 만 바꿔 같은 점검을 한다. 크기가 비슷한 다른 계열
   모델을 하나 이상 더 쓴다. 통과한 모델이 많을수록 검증된 스킬이다. 성능 좋은 모델에서 나빠지지 않았는지도 한 번 본다.

모델 서버가 여러 대면 모델마다 서버를 하나씩 정해 `--base-url` 을 달리하고 동시에 돌린다. 한 서버에 두 모델을
번갈아 보내면 모델을 바꿔 끼우느라 느려진다. 느리고 턴을 많이 쓰는 모델을 빠른 서버(GPU)에 둔다. 여러 서버를 한
주소로 묶은 풀(로드밸런서)은 요청마다 서버가 바뀌므로 점검에 쓰지 않고, 서버 주소를 직접 쓴다. 결과 기록은 파일을
잠그고 쓰므로 동시에 돌려도 섞이지 않는다.

스킬을 켜는 방식은 `--activation` 으로 고른다. 기본값은 `tool`(스킬 이름으로 부르는 전용 도구)이고, `file`(목록의
SKILL.md 경로를 파일로 읽기)도 있다. 작은 모델은 파일 읽기 방식에서 스킬을 건너뛰는 일이 많다. 그래서 기본 점검은
`tool` 로 하고, 필요하면 `file` 로도 확인한다.

생각(thinking) 모드를 지원하는 모델은 `--think` 로도 점검한다. 작은 모델은 생각 모드를 끄면 도구를 한 번 부르고
멈추거나, 하지 않은 일을 했다고 보고하는 경우가 많다. 생각 모드를 켜면 스킬 절차를 끝까지 따르는 경우가 크게 는다.
두 결과는 `results.json` 에 따로 남는다.

### 운영 환경을 다루는 스킬: 샌드박스에서 실행

클러스터·서버·홈 자동화처럼 실제 시스템을 바꾸는 스킬은 작업 PC 에서 모델 명령을 실행하면 안 된다. ssh 는 `$HOME` 을
바꿔도 실제 키를 쓴다. 명령만 막고 "절차를 설명하라"로 채점하면 작은 모델은 사용자에게 실행을 부탁하는 쪽으로 빠져
스킬 품질을 재지 못한다. 그래서 운영 환경을 축소한 **샌드박스 VM** 을 두고 모든 도구 호출을 그 안에서 실행한다.

- 샌드박스에는 스킬이 가정하는 구성을 작게 재현한다. 예: 단일 노드 쿠버네티스, GitOps 도구와 git 서버, 대시보드, 홈 자동화.
  모델은 sudo 없는 계정으로 쓰고, 운영 LAN 으로 나가는 연결은 막는다.
- 샌드박스 계정의 `~/.agents/environment.md` 에 가짜 환경 값을 둔다. 스킬의 "환경 정보 읽기" 단계가 그대로 동작한다.
- 깨끗한 상태를 스냅샷으로 두고 사례마다 되돌린다.

```bash
python3 scripts/local_eval.py run --skills <스킬 폴더들> --evals <스킬>/evals/sandbox.json \
  --remote <계정>@<샌드박스> --ssh-option=-i --ssh-option <전용 키> \
  --reset "<스냅샷 되돌리고 켜는 명령>" --ready "kubectl get nodes" --model <모델> --record
```

- `--remote` 면 파일 읽기·쓰기·목록·명령·확인 명령이 모두 원격에서 실행되고, 스킬 사본도 원격에 둔다.
- 샌드박스용 사례는 `evals/sandbox.json` 에 둔다. 설명형 사례(`evals.json`)는 샌드박스가 없을 때를 위해 남긴다.
- 확인 명령은 결과를 직접 본다. 예: git 원격에 커밋이 있는지, 동기화된 리비전, 배포된 설정 값, API 응답.
- 실제 도구처럼 사용자 전역 지침을 줄 때는 `--instructions <파일>` 을 쓴다. 샌드박스에는 일반 규칙만 담은 사본을 둔다.
- `--ready` 는 쿠버네티스 상태만 보지 말고 서비스에 실제로 요청해 확인한다. 스냅샷에서 되돌린 직후에는 옛 상태가
  "Ready" 로 남아 있다.
- 샌드박스를 여러 대 두면 모델 서버마다 한 대를 짝지어 병렬로 돌린다. 한 샌드박스를 두 실행이 같이 쓰면 되돌리기가
  서로의 작업을 지운다.
- 운영 스킬의 스크립트는 작업 PC 에서 한 줄로 부를 수 있게 만든다(예: `--kubectl "<kubectl 실행 명령>"`, 자격 증명은
  시크릿 이름으로 받음). 작은 모델은 `ssh 호스트 'python3 -' < 스크립트` 같은 조합을 자주 틀리고, 자격 증명을
  직접 꺼내다 출력한다.

### 저사양 모델에서 드러난 설명 작성 요령

- 작은 모델은 설명 속 **단어**에 끌린다. "…에는 쓰지 않는다" 문장에 적은 단어에도 끌린다. 제외 목록은 실제로
  헷갈리는 대상만 짧게 적는다.
- "서버에서 돌릴 스크립트", "'해 줘'라고만 해도" 같은 넓은 표현은 관련 없는 요청까지 끌어온다. 긍정 범위는 작업
  대상(예: `.py` 코드, 새 커밋)으로 좁게 시작한다.
- 쉬워 보이는 작업이면 모델이 스킬을 켜지 않고 바로 시작한다. 꼭 켜져야 하는 스킬은 "…을 하기 전에는 작업이
  간단해도 먼저 이 스킬을 켠다"처럼 적극적으로 쓴다. 그러면 근접 오답도 켜질 수 있으니 트리거 점검으로 균형을 본다.
- 작은 모델은 검증 명령 여러 개 중 일부를 빠뜨리거나, 실패한 채로 "끝났다"고 보고한다. 검증은 스크립트 하나로
  묶고, "통과하기 전에는 끝났다고 보고하지 않는다"를 절차에 쓴다.
- 작은 모델은 템플릿·뼈대 스크립트를 두고도 처음부터 새로 쓰곤 한다. "복사한다", "스크립트로 만든다"를 명령과
  함께 쓰고, 손으로 쓰면 무엇이 틀리는지 이유를 붙인다.
- 한 번 실행한 결과는 흔들린다. 질의마다 5번 돌려 비율로 판단한다. 설명을 고친 뒤에는 처음 보는 질의로 일반화를
  확인한다.

## 성능 좋은 모델로 품질 비교 (선택)

1. 스킬 폴더에 `evals/evals.json` 을 만든다. 처음에는 2~3개로 시작한다.

   ```json
   {
     "skill_name": "<이름>",
     "evals": [
       {
         "id": 1,
         "prompt": "<사용자가 실제로 칠 법한 요청. 경로, 이름, 맥락을 넣는다>",
         "expected_output": "<성공한 결과가 어떤 모습인지>",
         "files": [],
         "assertions": []
       }
     ]
   }
   ```

   - 격식 있는 요청과 짧고 대충 쓴 요청을 섞는다.
   - 경계 사례(애매한 입력, 규칙이 충돌하는 상황)를 하나 넣는다.
2. 각 사례를 **새 맥락에서** 두 번 실행한다. 한 번은 스킬 경로를 주고, 한 번은 주지 않는다(기존 스킬을 고치는
   경우에는 고치기 전 사본을 준다).
   - 하위 에이전트를 띄울 수 있으면 사례마다 하나씩 띄운다.
   - 없으면 도구의 새 세션이나 비대화형 실행으로 돌린다.
   - 결과물은 `<작업 폴더>/iteration-<N>/<사례>/{with_skill,without_skill}/` 에 저장한다.
3. 첫 결과를 본 뒤 `assertions` 를 채운다. 확인할 수 있는 문장으로 쓴다. 예: "출력이 올바른 JSON 이다",
   "검증 명령을 실행했다", "사용자에게 비밀값을 묻지 않았다". "잘했다" 같은 문장은 쓰지 않는다.
4. 각 assertion 을 PASS/FAIL 과 근거(출력의 인용)로 채점한다. 기계적으로 확인할 수 있는 것은 스크립트로 확인한다.
5. 해석:
   - 양쪽 다 항상 통과하는 assertion 은 스킬이 기여하지 않는 부분이다. 해당 지시를 줄인다.
   - 스킬이 있을 때만 통과하는 assertion 은 스킬의 가치다. 그 지시는 유지한다.
   - 실행할 때마다 결과가 다르면 지시가 모호하다는 뜻이다. 예시를 넣거나 기본값을 명확히 한다.
   - 실행 기록에서 헛걸음한 단계를 찾아, 그 원인이 된 지시를 고친다.
6. 고친 뒤 `iteration-<N+1>` 로 다시 돌린다. 개선이 멈추면 그만한다.

### 트리거 설명 다듬기

`description` 만 바꾸는 작업이다. 사용자가 실제로 칠 법한 질의 20개 정도를 만든다.

```json
[
  { "query": "<켜져야 하는 요청>", "should_trigger": true },
  { "query": "<비슷한 단어를 쓰지만 다른 작업인 요청>", "should_trigger": false }
]
```

- 켜져야 하는 질의에는 도메인 단어를 직접 쓰지 않는 요청을 포함한다.
- 켜지면 안 되는 질의는 키워드가 겹치는 근접 오답으로 만든다. 전혀 무관한 질의는 아무것도 시험하지 못한다.
- `scripts/local_eval.py trigger` 로 질의마다 5번 실행한다. 발동률 0.5 를 넘으면 통과로 본다.
- 질의의 60% 로 고치고, 나머지 40% 로 일반화됐는지 확인한다. 실패한 질의의 단어를 그대로 넣지 말고, 그 질의가
  대표하는 상황을 설명에 넣는다.
- 1024자 제한을 다시 확인한다.
