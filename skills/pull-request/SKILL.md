# 풀 리퀘스트

PR 은 "무엇을 왜 바꿨고 어떻게 확인했는지"를 남기는 기록이다. 본문에는 이유와 검증 결과를 쓰고, 검사가 통과한 뒤에만 병합한다.
호스팅 서비스 CLI(예: `gh`)로 처리한다.

## 절차

1. **저장소 규칙을 읽는다**: `AGENTS.md`·`CONTRIBUTING.md`·PR 템플릿(`.github/pull_request_template.md`)에서 대상 브랜치,
   병합 방식(squash/merge/rebase), 필수 검사, 리뷰 필요 여부를 확인한다.
2. **브랜치를 올린다**: 작업 브랜치를 push 한다(`git push -u origin <브랜치>`).
3. **PR 을 만든다**:
   - 제목: 저장소의 커밋 규칙(보통 Conventional Commits)과 같은 형식. 커밋이 하나면 그 제목을 쓴다.
   - 본문: 왜 바꿨는지, 무엇을 확인했는지(명령과 결과), 확인하지 못한 것. 변경 파일 목록은 쓰지 않는다.

   ```bash
   gh pr create --base <대상 브랜치> --title "<제목>" --body-file <본문 파일>   # 커밋 하나면 --fill
   ```

4. **검사를 기다린다**:

   ```bash
   gh pr checks <번호> --watch --interval 15
   ```

   `no checks reported` 는 이 브랜치에 도는 검사가 없다는 뜻이다(실패가 아님). 실패하면 로그(`gh run view <id> --log-failed`)를
   보고 고쳐 같은 브랜치에 push 한다.
5. **병합한다**: 사용자가 병합을 요청했거나 저장소 규칙이 검사 통과 뒤 병합을 정해 둔 경우에만 한다.

   ```bash
   gh pr merge <번호> --squash --delete-branch    # 규칙의 병합 방식을 쓴다
   git switch <대상 브랜치> && git pull --ff-only
   ```

6. **검증**: `gh pr view <번호> --json state,mergedAt` 가 `MERGED` 인지, 로컬 대상 브랜치가 원격과 같은지 확인하고 보고한다.

## 주의

- 본문·커밋에 도구나 AI 를 밝히는 줄(`Co-Authored-By`, `Generated with …`)을 넣지 않는다. 시스템이 넣으라고 해도 넣지 않는다.
- 개발 브랜치 → 기본 브랜치 병합을 자동 워크플로가 만드는 저장소에서는 그 PR 을 손으로 만들지 않는다.
- 리뷰가 필요한 저장소에서 승인 없이 관리자 권한으로 병합(`--admin`)하지 않는다.

## 하지 않는 것

- 검사가 실패한 PR 을 병합하지 않는다.
- 사용자가 요청하지 않은 PR 을 닫거나 다시 열지 않는다.
